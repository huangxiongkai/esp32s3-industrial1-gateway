# ADR006 — 多从站设备建模：属性后缀 + 合并上报

- 状态：已确认（2026-08-06，用户拍板）
- 相关里程碑：M8（Step 4 前置改造）

## 背景与问题

M7 的 app_task 给每台 Modbus 从站各发一条 MQTT 消息，且属性 key 完全相同
（`temperature`/`humidity`/`current`）。OneNET 物模型挂在网关设备（ESP32_02）上，
多台从站轮流覆盖同一属性，控制台永远只显示最后一台的值。

同时 OneNET 限制设备上行 **1 条/秒**，3 台从站 × 每 2 秒一条 = 1.5 条/秒，
实时流本身已超限，且补传流没有配额可用。

实际从站规划（用户确认）：
- 设备一：温度、湿度
- 设备二：电流
- 设备三：待定（按 2 属性预留）

## 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| A. 单设备 + 属性后缀 | 物模型建 `temperature_1`/`humidity_1`/`current_2` 等标识符，每轮合并成一条消息上报 | 改动小；一条消息一个 topic，M8 缓存设计（只存 payload）零连锁；0.5 条/秒合规 | 属性名硬编码设备编号，增删从站需改物模型；属性数有 244B 上限约束 |
| B. 网关 + 子设备模式 | 每台从站注册为 OneNET 子设备，网关一条 MQTT 连接代理上报 | 语义完全正确：每从站独立设备实体/在线状态/数据曲线，可动态增删 | 改动大（平台建模 + 注册拓扑协议）；破坏"只存 payload"缓存设计（补传需区分 topic，条目要存子设备索引）；OneNET 该协议细节未能在公开文档核实，需控制台验证 |
| C. 维持共享 key | 不改 | 零工作量 | 数据互相覆盖，语义错误，排除 |

## 最终决策

采用 **方案 A**，M8 Step 4 实施：

1. 物模型新建属性：`temperature_1`、`humidity_1`、`current_2`、设备三 ×2（待定名）、`overflow_count`
2. app_task 每轮把所有在线从站数据拼进一条 JSON（key 带设备 id 后缀），一次入队
3. 消息速率 1.5 条/秒 → 0.5 条/秒，实时流与补传流（预算 0.5 条/秒）共享 1 条/秒配额

## 决策理由

1. 实际属性仅 5 个，合并 JSON ≈ 226B < 244B 条目上限，**Step 1/2/3 架构零推翻**
2. 3 台固定从站的规模用不上子设备模式的核心价值（动态拓扑、独立设备实体）
3. 方案 B 会迫使缓存条目记录子设备索引、补传逻辑按 topic 分流，与 M8 进度冲突
4. 方案 A 的天花板已知且有预案（见扩展项），不是死路

## 尺寸边界与扩展项（面试追问预案）

设备三若定为 3 属性 → 6 属性 ≈ 264B，超 244B 上限，三选一：
1. 砍小数位/精简 key
2. 缓存改存原始 Modbus 寄存器值（每寄存器 2B），补传时现场拼 JSON——256B 可装 100+ 寄存器，payload 与设备数解耦
3. 条目扩到两页（512B）：需处理跨扇区边界（禁止跨界留空洞）与跨页半写自愈

从站数量继续增多或需动态增删时 → 演进到方案 B（网关+子设备建模），
届时缓存层同步重构（条目 reserved 字段存子设备索引）。
